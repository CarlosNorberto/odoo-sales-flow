Odoo Sales Flow

Guía de implementación del flujo de ventas completo en Odoo vía JSON-RPC. Los conceptos y la estructura de los requests aplican a cualquier lenguaje con soporte HTTP y JSON.

Conexión y autenticación

Toda comunicación con Odoo se hace mediante HTTP POST a un único endpoint: {ODOO_URL}/jsonrpc. No hay múltiples endpoints por recurso como en REST — el modelo y método a ejecutar van dentro del body del request.

Antes de cualquier operación hay que autenticarse para obtener el uid (user ID). Este número se envía en cada request posterior junto con la contraseña. No hay tokens ni sesiones con estado — cada llamada se autentica por sí sola.

request de autenticación
{
  "jsonrpc": "2.0",
  "method":  "call",
  "id":      1,
  "params": {
    "service": "common",
    "method":  "login",
    "args":    ["nombre_db", "usuario", "password"]
  }
}
Importante
Odoo devuelve HTTP 200 aunque las credenciales sean incorrectas. Si el login falla, result es false o null — no hay un error HTTP. Siempre verificar el valor de result explícitamente antes de continuar.

Estructura de todos los requests posteriores

Una vez obtenido el uid, todos los requests usan service: "object" y method: "execute_kw":

estructura base — cualquier operación
{
  "jsonrpc": "2.0",           // siempre 2.0
  "method":  "call",          // siempre "call"
  "id":      1,               // cualquier número o string, para correlacionar respuestas
  "params": {
    "service": "object",      // siempre "object" para operaciones en modelos
    "method":  "execute_kw",  // siempre "execute_kw" para operaciones en modelos
    "args": [
      "nombre_db",            // base de datos
      2,                      // uid obtenido al autenticar
      "password",             // contraseña (va en cada request)
      "sale.order",           // modelo de Odoo
      "create",               // método del modelo
      [[{ ... }]],            // argumentos posicionales
      {}                      // argumentos nombrados (kwargs)
    ]
  }
}

El campo id del request

El id es parte del protocolo JSON-RPC 2.0, no de Odoo. Sirve para correlacionar requests y responses en sistemas asíncronos donde múltiples llamadas pueden estar "en vuelo" al mismo tiempo. Odoo siempre responde de forma sincrónica, por lo que puede ser cualquier número o string. Para sistemas con colas de mensajes o workers en paralelo, usar un identificador único y significativo (ej. "orden-juan-1711234500") permite saber exactamente a qué solicitud corresponde cada respuesta.

Errores de negocio vs errores de red

Hay dos tipos de error con mecanismos distintos de detección:

TipoCómo se detectaDónde está el mensaje

Error de negocio HTTP 200, verificar response.error response.error.data.message
estructura de respuesta con error de negocio
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": 200,
    "message": "Odoo Server Error",
    "data": {
      "name":    "odoo.exceptions.ValidationError",

    }
  }
}

Flujo de ventas

El flujo completo involucra 6 operaciones en orden estricto. Cada una depende del resultado de la anterior.

1
Autenticar
Obtener el uid del usuario. Se reutiliza en todos los requests siguientes.
service: common / method: login
2
Crear venta
Genera sale.order en estado draft. No mueve inventario ni genera asientos contables todavía.
sale.order → create → retorna [saleId]
3
Confirmar venta
Cambia el estado a sale. Como efecto colateral, Odoo genera automáticamente una orden de entrega (stock.picking) en el almacén.
sale.order → action_confirm
4
Validar salida de productos
Obtener el picking_id asociado a la venta, luego validarlo. Este paso tiene lógica condicional — ver sección detallada abajo.
stock.picking → search_read + button_validate
5
Crear factura
Se usa un wizard (sale.advance.payment.inv) — no se crea el account.move directamente. Ver sección detallada abajo.
sale.advance.payment.inv → create + create_invoices
6
Confirmar factura
Publica la factura cambiando su estado a posted. Lista para pago y contabilidad.
account.move → action_post

Detalle — Crear venta

El modelo sale.order requiere un partner y al menos una línea de producto. Los campos partner_id, product_id y tax_id esperan IDs numéricos, no nombres. Para obtener esos IDs a partir de nombres estables entre instalaciones, usar XML IDs — ver sección XML IDs más abajo.

args para crear una venta con líneas
args: [[{
  "partner_id": 14,
  "date_order":  "2026-03-01",
  "order_line": [
    [0, 0, {                        // [0,0,{}] = crear línea nueva
      "product_id":      42,
      "product_uom_qty": 1,
      "price_unit":      100.0,
      "tax_id": [[6, 0, [5, 8]]]    // [6,0,[ids]] = reemplazar relación
    }]
  ]
}]]

Comandos de campos relacionales

ComandoQué haceCuándo usarlo
[0, 0, {...}]Crea un registro y lo vinculaLíneas de orden, líneas de factura
[6, 0, [ids]]Reemplaza toda la relación con los IDs dadosImpuestos, etiquetas
[4, id, 0]Vincula un registro existente sin tocar los demásAgregar un ítem a una lista existente

Retorno: create devuelve un array con el ID del registro creado: [57].

Detalle — Validar salida de productos

Este es el paso más complejo porque button_validate puede retornar cosas distintas dependiendo del estado del inventario y la configuración de Odoo. Nunca asumir que retorna un valor fijo — siempre verificar res_model en la respuesta.

Paso 1 — Obtener el picking de la venta

Al confirmar la venta, Odoo crea automáticamente un stock.picking. Hay que buscarlo por el ID de la venta:

buscar el picking asociado
modelo:  "stock.picking"
método:  "search_read"
args:    [[["sale_id", "=", 57]]]
kwargs:  { "fields": ["id"], "limit": 1 }

retorna: [{ "id": 35 }]

Paso 2 — Validar con button_validate

button_validate puede retornar tres cosas distintas:

RetornoQué significaQué hacer
true Stock suficiente, picking validado directamente Nada más — el picking ya está en done
res_model: "confirm.stock.sms" Odoo quiere enviar SMS de confirmación al cliente Llamar action_cancel o action_confirm en ese wizard
res_model: "stock.backorder.confirmation" Stock insuficiente para algún producto Crear y procesar el wizard de backorder
Por qué button_validate interrumpe el flujo
Internamente, button_validate llama a _pre_action_done_hook() antes de ejecutar _action_done() (que es quien realmente mueve el stock). Si ese hook retorna algo distinto de True, _action_done() nunca se ejecuta — el stock no se mueve hasta que se resuelva el wizard pendiente.

Manejo del backorder

El wizard de backorder no viene pre-creado en el retorno de button_validate — Odoo solo retorna la acción para abrirlo. Hay que crearlo explícitamente usando el context que viene en la respuesta:

flujo completo de validación
1. Llamar button_validate en stock.picking

2. Verificar el retorno:

   si result === true:
     → picking en done, no hay nada más que hacer

   si result.res_model === "confirm.stock.sms":
     → llamar action_cancel en confirm.stock.sms con result.res_id
     → el picking queda validado sin enviar SMS

   si result.res_model === "stock.backorder.confirmation":
     → crear wizard:
          modelo:  "stock.backorder.confirmation"
          método:  "create"
          args:    [{ "pick_ids": result.context.default_pick_ids }]
     → procesar wizard:
          método:  "process"
          args:    [[wizard_id]]
     → resultado: picking original en done
                  nuevo picking en ready (para las unidades pendientes)
Qué es un backorder
Si la venta pide 10 unidades pero solo hay 7 en stock, Odoo valida la entrega de las 7 disponibles (picking original → done) y crea un segundo picking en estado ready para las 3 restantes. Ese segundo picking es el backorder y se resolverá cuando haya stock disponible.
No usar skip_backorder
Existe un contexto skip_backorder: true que omite el wizard y valida lo disponible sin crear picking pendiente. Las unidades faltantes quedan sin registro — el cliente pagó por ellas pero Odoo no tiene ningún documento de deuda pendiente. No usar en flujos de venta reales.

Detalle — Crear y confirmar factura

La factura no se crea directamente en account.move. Se usa el wizard sale.advance.payment.inv, que replica el flujo interno de Odoo y garantiza que la factura quede correctamente vinculada a la venta y sus líneas.

paso 1 — crear el wizard
modelo:  "sale.advance.payment.inv"
método:  "create"
args:    [{
  "sale_order_ids":        [[6, 0, [saleId]]],
  "advance_payment_method": "delivered"   // facturar lo entregado
}]

retorna: [wizardId]
paso 2 — ejecutar el wizard
modelo:  "sale.advance.payment.inv"
método:  "create_invoices"
args:    [[wizardId]]

retorna: { "res_id": invoiceId, ... }   // res_id es el ID del account.move creado
paso 3 — confirmar la factura
modelo:  "account.move"
método:  "action_post"
args:    [[invoiceId]]

estado resultante: posted
advance_payment_methodQué factura
"delivered"Lo que fue entregado — para flujo estándar
"percentage"Un porcentaje del total como adelanto
"fixed"Un monto fijo como adelanto
Validar el stock antes de facturar
Si se intenta crear la factura con "delivered" sin haber validado el picking previamente, el wizard retorna result: null porque no hay nada entregado que facturar. Siempre respetar el orden del flujo.

XML IDs — Referencias portables

Los IDs numéricos de Odoo varían entre instalaciones. El cliente con ID 14 en un servidor puede ser el 37 en otro. Para hacer integraciones portables, Odoo provee los XML IDs: identificadores de texto estables con formato modulo.nombre que resuelven siempre al mismo registro.

Para convertir un XML ID a ID numérico se consulta el modelo ir.model.data:

resolver xmlid "base.res_partner_12" a ID numérico
modelo:  "ir.model.data"
método:  "search_read"
args:    [[["module", "=", "base"], ["name", "=", "res_partner_12"]]]
kwargs:  { "fields": ["res_id"], "limit": 1 }

retorna: [{ "res_id": 14 }]   // 14 es el ID numérico en esa instalación

Para encontrar XML IDs en Odoo activar el modo desarrollador y navegar a:
Ajustes → Técnico → Secuencias e identificadores → Identificadores externos

Buenas prácticas

PrácticaMotivo
Credenciales en variables de entorno Nunca hardcodear URL, DB, usuario o contraseña en el código
Verificar response.error, no solo el HTTP status Odoo devuelve HTTP 200 aunque la operación falle internamente
Usar XML IDs en lugar de IDs numéricos Los IDs numéricos varían entre instalaciones y entornos
Usar wizards cuando la UI los usa Saltear un wizard generalmente produce registros inconsistentes
Verificar el res_model del retorno de button_validate Puede retornar distintos wizards según stock y configuración de Odoo
Centralizar la lógica de comunicación Un único método que construye y envía requests evita repetir lógica
Respetar el orden del flujo Confirmar antes de buscar el picking, validar stock antes de facturar

Errores comunes

ErrorCausaSolución
result: false en login Credenciales incorrectas o DB inexistente Verificar URL, nombre de DB, usuario y contraseña
Access Denied Sin permisos sobre el modelo Asignar grupos en Odoo: Ventas, Inventario, Facturación
XML ID not found El XML ID no existe en esa instancia Verificar en ir.model.data con modo desarrollador
No pickings found La venta no fue confirmada antes de buscar el picking Respetar el orden: crear → confirmar → buscar picking
result: null al crear factura El picking no fue validado, no hay nada entregado Validar el stock picking antes de llamar create_invoices
button_validate retorna wizard inesperado Configuración de Odoo activa wizards adicionales (SMS, reportes) Verificar res_model y manejar cada caso explícitamente
ECONNREFUSED URL o puerto incorrectos, Odoo no está corriendo Verificar URL y puerto en las variables de entorno
